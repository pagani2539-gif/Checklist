# ADR 0001: Local-first Checklist MVP

สถานะ: ยอมรับสำหรับการทดสอบเบื้องต้น; ขอบเขต local-first เดิมถูกเสริมด้วย ADR 0004 สำหรับ server/public readiness

หมายเหตุสถานะ: ADR ฉบับนี้บันทึกขอบเขตของ MVP ระยะแรก ไม่ได้อ้างว่า repository ปัจจุบันไม่มี server code แล้ว หากพูดถึง central persistence, OIDC หรือ public deployment ให้ยึด [ADR 0004](0004-central-persistence.md), [API contract](../api-contract.md) และ runbook ปัจจุบัน

## Context

ไฟล์ `Checklist ตัวอย่างเอกสาร.pdf` เป็นแบบฟอร์มตรวจงานที่สร้างจาก Excel มี 14 หน้า หน้าแรกเป็นข้อมูลโครงการและสารบัญ BOQ ส่วนหน้าถัดไปแบ่งเป็นหมวดอุปกรณ์/งาน เช่น WIM Sensor, WIM Control, LPR, กล้อง, NVR, Database, งานทำความสะอาด และ VMS โดยหลายช่องใน PDF เป็นช่องภาพและหมายเหตุ

คำขอรอบนี้ต้องการ MVP ที่กรอกค่าตัวเลขและเลือกสถานะรายการตรวจได้ง่าย เพื่อทดสอบระบบก่อน จึงยังไม่ควรผูกกับระบบฐานข้อมูล บัญชีผู้ใช้ หรือขั้นตอนการอนุมัติ

## Decision

สร้างเว็บแบบ static ที่รันด้วย Node.js built-in server ได้ โดยมี:

- ข้อมูลประจำรอบการตรวจ 5 ช่อง: ชื่อโครงการ, วันที่ตรวจ, ผู้รับจ้าง, เลขที่สัญญา และผู้ตรวจสอบ
- Checklist 13 หมวดตามสารบัญใน PDF
- แต่ละรายการมีค่าตัวเลขแบบ optional, สถานะ และหมายเหตุ
- สถานะรายการตรวจ: ยังไม่ตรวจ, ปกติ, ชำรุด, อยู่ระหว่างรอเปลี่ยนทดแทน, ไม่ได้ติดตั้ง และไม่เกี่ยวข้อง
- สรุปจำนวนรายการที่ตรวจแล้ว, รายการที่มีปัญหา และ progress
- บันทึกอัตโนมัติใน `localStorage` พร้อมปุ่มโหลดข้อมูลตัวอย่าง, ล้างข้อมูล และพิมพ์
- แยก `MASTER_CHECKLIST_SECTIONS` เป็นการตั้งค่ารายการตรวจประจำสถานี, `stationProfiles` เป็นข้อมูลประจำสถานี (Station Profile) และ `inspectionSnapshot` เป็นข้อมูล ณ วันที่เริ่มรอบการตรวจ (Snapshot)
- สร้าง workspace การตรวจแยกตามสถานีใน localStorage เพื่อให้การสลับสถานีไม่ปนค่าตรวจ และเก็บรายการเดิมใน `inspectionHistory` แบบ snapshot
- รายการซ้ำตามอุปกรณ์จริง เช่น Sensor, Loop และ Camera; รายการที่ไม่มีอุปกรณ์จะเป็น `ไม่เกี่ยวข้อง` และไม่นับใน progress
- UI ภาษาไทยและ responsive สำหรับการใช้งานหน้างาน
- แยก workflow ด้วย Hash Route ในหน้า static เดียว: Dashboard, Stations, Inspection Rounds, Checklist และ History
- ใช้ `inspectionRounds` เป็นข้อมูลหลักของรอบตรวจ โดยแต่ละรอบมี `stationId`, สถานะ `draft/closed`, metadata, `snapshot` และ `inspectionItems`
- การสร้างรอบการตรวจต้องกดเริ่มอย่างชัดเจนเพื่อสร้างข้อมูล ณ วันที่เริ่มรอบการตรวจ (Snapshot); รอบที่ปิดแล้วเป็นแบบอ่านอย่างเดียว และการแก้ไขหลังปิดให้จัดทำรอบการตรวจใหม่
- MVP เฟสนี้เป็นเครื่องเดียว/จัดเก็บภายในเครื่อง ไม่มี Backend, Authentication, ผู้ตรวจทาน หรือ Approval; `ผู้ใช้เครื่องนี้` เป็นเพียงข้อความแสดงผล ไม่ใช่การยืนยันตัวตนหรือมาตรการควบคุมความปลอดภัย
- Flow สร้างรอบเป็น Wizard 3 ขั้น และหน้า Checklist แสดงทีละรายการ พร้อม close-readiness warning ที่สรุปรายการค้างและให้ผู้ใช้ยืนยันปิดได้
- ประวัติเป็นแบบอ่านอย่างเดียวจริง; `createRevisionRound` คัดลอกข้อมูลประจำรอบ/ผลตรวจไปเป็นฉบับร่างใหม่ เก็บเหตุผลและข้อมูลกำกับฉบับแก้ไข โดยไม่เขียนทับรอบต้นฉบับ
- สถานีหรือ Asset ที่มีประวัติอ้างอิงห้าม hard-delete ใช้ `active: false` เพื่อปิดใช้งาน/เก็บถาวร
- `inspectionWorkspaces`, `inspectionHistory`, `items`, `inspectionSnapshot` และ `activeStationId` ยังคงเป็น compatibility aliases ระหว่าง migration ของ `checklist-mvp-v1`; migration ใหม่เป็น additive และไม่ล้าง evidence เดิม

## Scope boundary

ช่องหลักฐานใน PDF มีสถานะและไฟล์แนบแบบจัดเก็บภายในเครื่องแล้ว แต่การพิสูจน์บนอุปกรณ์จริง, field/UAT, sync, multi-user, authentication, ระบบฐานข้อมูล และการติดตั้งใช้งานจริงยังอยู่นอกขอบเขต MVP นี้

## Consequences

ผู้ใช้สามารถทดสอบขั้นตอนหลักได้ทันทีโดยไม่ต้องเตรียม service ภายนอก แยกข้อมูลสถานีและรอบการตรวจได้ และเก็บประวัติแบบ Snapshot ที่ไม่เปลี่ยนแปลง แต่ข้อมูลจะอยู่เฉพาะ browser เครื่องที่ใช้งาน และยังไม่มีการตรวจสอบว่าค่าตัวเลขผ่านเกณฑ์ทางวิศวกรรม เพราะ PDF ไม่ได้ให้เกณฑ์หรือหน่วยวัดที่เป็นมาตรฐานเดียวกันสำหรับทุกรายการ

ข้อมูล `ผู้จัดทำรายงาน`, `ผู้ตรวจสอบรายงาน`, `ผู้มีอำนาจลงนาม` และ `วันที่ลงนาม` เป็นข้อมูลลงนามรายงานเท่านั้น ไม่ใช่ขั้นตอนการอนุมัติของระบบ
