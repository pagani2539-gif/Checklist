# แผนจัดโครงสร้างไฟล์รูปภาพ Checklist

Status: ready-for-human
วันที่: 2026-10-06
ขอบเขตที่อนุมัติล่าสุด: ดำเนินการปรับระบบ สำรองข้อมูล และจัดโฟลเดอร์จริงตามคำสั่งผู้ใช้
ผลดำเนินการ: เสร็จแล้ว ดู verification.md; เก็บสำเนาเดิมและสำรองข้อมูลไว้ ไม่ลบหลักฐาน

## เป้าหมายและหลักฐาน

แยกไฟล์ตามด่านและรอบตรวจเพื่อค้นและสำรองข้อมูลเป็นส่วน ๆ โดยรักษารหัสรูป ความสัมพันธ์ ประวัติ และ Snapshot เดิม

ตรวจพบ data/attachments มี 6,466 ไฟล์ ไม่มีโฟลเดอร์ย่อย รวมประมาณ 0.77 GiB ณ เวลาสำรวจ ค่า .env กำหนด filesystem และ ./data/attachments; /ready ที่พอร์ต 5220 ยืนยัน backend filesystem พร้อมใช้งาน

- server/attachment-store.mjs ใช้ path.basename จึงยังอ่านตำแหน่งที่มีโฟลเดอร์ย่อยไม่ได้
- server/api.mjs สร้างชื่อ UUID และบันทึก storageName, stationId, hash และวันที่อัปโหลดในฐานข้อมูล
- src/domain/server-storage.js ส่ง stationId แต่ยังไม่มี roundId หรือประเภทหลักฐาน
- ChecklistPage.jsx, VehicleApiReviewPage.jsx และ vehicle-evidence-images.js เป็นจุดส่งรูปที่ต้องครอบคลุม
- vehicle-evidence-images.js ใช้ไฟล์ร่วมจาก URL เดียวกันภายในด่านได้ ต้องรักษาการอ้างอิงร่วม
- ADR 0004 กำหนดข้อมูลส่วนกลางและมี S3 เป็นเป้าหมาย; ADR 0006 ห้ามลบรูปที่ยังมีผู้ใช้อ้างอิง; ADR 0010 แยกต้นฉบับกับ WebP

## โครงสร้างเป้าหมาย

```text
data/attachments/
  stations/<stationId>/<year>/rounds/<roundId>/
    inspection/originals/<uuid>.<ext>
    vehicle-api/originals/<uuid>.<ext>
    vehicle-api/webp/<uuid>.webp
  stations/<stationId>/unassigned/<year>/<uuid>.<ext>
  unassigned/<year>/<uuid>.<ext>
```

ใช้รหัสคงที่ ไม่ใช้ชื่อด่านหรือวันที่ที่แก้ไขได้เป็นตัวตนของโฟลเดอร์ ปีของไฟล์ใหม่มาจากเวลาสร้างไฟล์บนเซิร์ฟเวอร์ใน Asia/Bangkok และไม่เปลี่ยนเมื่อแก้ข้อมูลรอบ ส่วนชื่อด่าน วันที่ตรวจ และชื่อรูปเดิมอยู่ในฐานข้อมูล/รายการกำกับ ไฟล์ที่ใช้หลายรอบอยู่ตำแหน่งเจ้าของเดิม ไม่ทำสำเนาหรือย้ายเมื่อสร้างรอบแก้ไข

ไม่แยกตามระบบหรืออุปกรณ์ในระยะแรก เพราะความสัมพันธ์อาจเปลี่ยนและรูปหนึ่งอาจถูกใช้ร่วม ให้ค้นจากข้อมูลรอบแทน ไม่ย้าย public/report ซึ่งเป็นภาพประกอบแอป ไม่ใช่หลักฐานตรวจ

## ลำดับงาน

### 1. สำรวจข้อมูลและสร้างรายการก่อนย้าย

อ่านฐานข้อมูลที่ระบบกำลังใช้และไฟล์แบบอ่านอย่างเดียว จัดทำรายการ id, storageName เดิม, stationId, รอบที่อ้างอิง, ประเภท, ขนาด, hash, สถานะลบ และตำแหน่งใหม่ ตรวจทุกจุดอ้างอิง รวมรูปผู้ตรวจ ภาพรถ WebP รอบแก้ไข รายงาน และข้อมูลประวัติที่นโยบายกำหนดให้เก็บ

แยกไฟล์ขาด ไฟล์ที่ไม่พบ metadata ข้อมูลหลายรายการชี้ไฟล์เดียว รูปอ้างอิงข้ามด่าน และรูปที่จัดกลุ่มไม่ได้ ห้ามเดาจากชื่อไฟล์หรือถือไฟล์ไม่พบผู้ใช้งานว่าเป็นขยะ ห้ามลบอัตโนมัติ รายการที่กำกวมคงตำแหน่งเดิมจนตรวจสอบได้

### 2. รองรับตำแหน่งใหม่พร้อมอ่านรูปเก่า

ปรับตัวเก็บไฟล์ให้รับ relative storage key และสร้างโฟลเดอร์แม่ได้ อ่าน/ลบทั้งชื่อเดิมและชื่อที่มีโฟลเดอร์ย่อย โดยตรวจขอบเขต root จริง ปฏิเสธ absolute path, .. และทางเชื่อมที่ออกนอก root ใช้รูปแบบ key เดียวที่รองรับ filesystem และ S3

คง attachment ID และเส้นทาง API เดิม ให้ฐานข้อมูลระบุตำแหน่งที่ใช้จริง ไม่แก้ Snapshot เพื่อเปลี่ยน path

### 3. จัดรูปใหม่อัตโนมัติ

เพิ่ม roundId และประเภทภาพในคำขออัปโหลดและ metadata ตามที่จำเป็น เซิร์ฟเวอร์ตรวจว่ารอบเป็นของด่าน ผู้ใช้มีสิทธิ์ และประเภทอยู่ในรายการที่อนุญาต เซิร์ฟเวอร์สร้าง key เอง ไม่รับ path จากผู้ใช้

ครอบคลุมรูปตรวจทั่วไป รูปที่เพิ่มในหน้าตรวจรถ ภาพรถต้นฉบับ และสำเนา WebP ตรวจพฤติกรรม reuse ของภาพรถก่อนเพิ่ม roundId เพื่อไม่สร้างภาพซ้ำโดยไม่จำเป็น

คำขอจากหน้าจอรุ่นเก่าที่ส่งเฉพาะ stationId ยังทำงานได้ผ่าน unassigned ของด่าน; กรณีไม่มี stationId ต้องคงกติกาสิทธิ์เดิม ไม่ใช้ fallback เพื่อข้ามสิทธิ์

### 4. ย้ายรูปเก่าแบบทำซ้ำและหยุดต่อได้

ทำเครื่องมือดูแผนก่อนทำจริง บันทึก manifest และ checkpoint ทุกไฟล์ สำรองฐานข้อมูลและไฟล์เป็นชุดที่สัมพันธ์กันก่อนเริ่ม

สำหรับไฟล์ที่ระบุเจ้าของได้ เลือกรอบเจ้าของด้วยกติกาคงที่จากวันที่สร้างรอบและรหัสรอบ ไม่ใช้วันที่แก้ไขล่าสุด หากไม่ชัดเจนเก็บใน unassigned หรือคงเดิมตามรายการตรวจสอบ

ขั้นตอนต่อไฟล์: คัดลอกไปตำแหน่งใหม่ → ตรวจขนาดและ SHA-256 → เปลี่ยน storageName ในฐานข้อมูลแบบตรวจค่าเดิมก่อนแก้ → ทดลองอ่านผ่าน API โดยคงไฟล์เก่าไว้ เมื่อทำซ้ำต้องตรวจไฟล์ปลายทาง ไม่เขียนทับไฟล์ที่ hash ต่างกัน

ใช้ช่วงบำรุงรักษาหรือกลไกหยุดเขียน/ลบเพื่อไม่ให้การอัปโหลดและการลบชนกับการย้าย ตรวจไฟล์และ metadata อีกครั้งก่อนเปลี่ยนตำแหน่ง ไม่ฟื้น metadata ที่ถูกลบแล้ว

### 5. ตรวจและเปิดใช้งาน

ทดสอบด้วยฐานข้อมูลและไฟล์สำเนาก่อน ระบบจริงเริ่มจากหนึ่งด่าน แล้วขยายเมื่อผ่านเกณฑ์ เก็บผลแยกระหว่างการทดสอบ ชุดข้อมูลสำเนา และการเปิดรูปจริงที่มีสิทธิ์

หลังยืนยันครบจึงเสนอรายการสำเนาตำแหน่งเก่าที่จะลบและระยะเก็บคืน การลบไฟล์เก่าเป็นขั้นแยกที่ต้องได้รับคำสั่งชัดเจน ไม่รวมการลบในเครื่องมือย้ายเริ่มต้น

## เกณฑ์ผ่าน

- อ่าน อัปโหลด และลบรูปได้ทั้ง key เดิมและใหม่; ป้องกัน path ออกนอก root
- รูปต้นฉบับทุกไฟล์ที่ย้ายมีขนาดและ hash ตรงเดิม รหัสรูปและ Snapshot ไม่เปลี่ยน
- การย้ายซ้ำ การหยุดกลางทาง และความผิดพลาดระหว่างคัดลอก/แก้ฐานข้อมูลไม่ทำให้รูปหาย
- รอบที่ใช้รูปเดียวกันยังอ่านได้ และลบรอบหนึ่งไม่กระทบอีกรอบ
- ตรวจรูปในรอบเปิด รอบปิด รอบแก้ไข รายงานปกติ และรายงานรถ รวมต้นฉบับ/WebP
- คำขอจากหน้าจอรุ่นเก่าใช้งานได้ตามสิทธิ์; รายการไม่ระบุเจ้าของไม่สูญหาย
- จำนวนไฟล์ metadata การอ้างอิง และผล hash ตรงรายการย้าย อธิบายทุกข้อยกเว้นได้
- /health และ /ready ผ่าน พร้อมยืนยันว่าแอปที่ให้บริการเป็นรุ่นใหม่

## การย้อนกลับ

หยุดงานย้าย ใช้ manifest คืนเฉพาะ storageName ที่ยังตรงกับรายการย้าย และอ่านไฟล์เดิมที่ยังเก็บไว้ ห้ามคืนทั้งฐานข้อมูลทับงานใหม่โดยไม่ประเมินผล รูปใหม่ที่อัปโหลดหลังปรับระบบต้องยังอ่านได้ จึงใช้รุ่นที่รองรับ key ทั้งสองแบบเป็นฐานย้อนกลับ ไม่ย้อนเป็นรุ่นที่อ่านโฟลเดอร์ย่อยไม่ได้จนกว่าจะจัดการรูปใหม่ครบ

## ขอบเขตที่ไม่รวม

ไม่ลบรูปซ้ำ ไม่ลดคุณภาพต้นฉบับ ไม่ล้างประวัติ ไม่เปลี่ยน Snapshot และไม่เปลี่ยนไปใช้ S3 ในงานนี้ การแบ่งโฟลเดอร์ช่วยจัดการข้อมูล แต่ไม่ลดพื้นที่เก็บรวมและยังไม่ใช่หลักฐานว่าการเปิดรูปเร็วขึ้น
