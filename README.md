# Checklist Operations Hub

เว็บ Checklist ภาษาไทยสำหรับตรวจอุปกรณ์ตามไฟล์แนบ BOQ 13 หมวด โดยใช้ `checklist-master-v5-system-mapped` เป็นแม่แบบปัจจุบันสำหรับรอบใหม่, `checklist-master-v4-asset-mapped` เป็นแม่แบบเดิม และ `checklist-master-v3-boq-evidence` เป็นแม่แบบประวัติเดิม ใช้นโยบายทำความสะอาดอุปกรณ์ `equipment-cleaning-v1`

สถานะเอกสารอ้างอิงล่าสุด: 24 กันยายน 2569 ดูสรุปความต่างระหว่างเอกสารปัจจุบันกับรายงานตรวจย้อนหลังที่ [Document Status](docs/document-status.md)

ระบบมีสองโหมดการทำงาน: `VITE_STORAGE_MODE=local` สำหรับ local-first ที่เก็บ state ใน `localStorage` และไฟล์ใน IndexedDB ของ browser เครื่องนั้น และ `VITE_STORAGE_MODE=server` สำหรับโหลด/บันทึกผ่าน `/api/v1/state` และ API ไฟล์แนบ โดย server ใช้ PostgreSQL และเลือก filesystem หรือ S3-compatible สำหรับไฟล์ได้. การติดตั้ง local/pilot ที่เลือกไว้ใช้บัญชีภายใน PostgreSQL ให้ผู้ดูแลสูงสุดสร้างผู้ใช้และกำหนด role/สถานี; OIDC ก็มี authentication flow รองรับเมื่อกำหนดค่า identity provider ขององค์กร แต่ไม่ใช่รูปแบบที่เลือกไว้ใน ADR 0005. การใช้บัญชีภายในไม่ต้องใช้ OIDC หรือ Docker สำหรับ login

Workflow สร้างรอบตรวจเลือก Contract, Work Package และสถานีจากบริบทเดียวกันก่อนบันทึกรอบ; Contract Work Report แยกจากรายงานตรวจสถานี ดูเส้นทางปัจจุบันที่ [Route Map](docs/design-system/route-map.md)

## เปิดใช้งาน

ต้องมี Node.js ติดตั้งอยู่แล้ว สำหรับ local mode ให้ใช้ `.env` ที่ไม่เปิด `VITE_STORAGE_MODE=server` และไม่ตั้ง `CHECKLIST_STORAGE_BACKEND=postgres`/`CHECKLIST_ATTACHMENT_BACKEND=s3` หากยังไม่มี service เหล่านั้น จากโฟลเดอร์นี้จึงรัน:

```powershell
node --env-file=.env server.mjs
```

แล้วเปิด `http://127.0.0.1:5220` ใน browser

`.env.example` เป็น template ที่รวมค่าของ server (`server` + PostgreSQL + S3 + local accounts) ไม่ควรคัดลอกแล้วรันโดยไม่เตรียม service และ secret ให้ครบ. ถ้าใช้ PostgreSQL ที่ติดตั้งไว้แล้วกับไฟล์แนบในเครื่อง ให้ตั้ง `CHECKLIST_ATTACHMENT_BACKEND=filesystem` สำหรับ local/pilot

สำหรับ local/pilot ที่มี PostgreSQL อยู่แล้ว สามารถใช้ filesystem attachments ได้โดยไม่ต้องใช้ OIDC, Docker หรือ S3. สร้าง Admin เริ่มต้นได้ครั้งเดียวด้วย `npm.cmd run admin:bootstrap-default`; ระบบสร้าง username `admin`, คัดลอกรหัสสุ่มลง clipboard และบังคับเปลี่ยนรหัสหลัง login แรก. ผู้ดูแลสร้างบัญชีผู้ใช้จากเมนู “จัดการผู้ใช้”. ก่อนเปิด Public production ให้เตรียม S3-compatible storage, HTTPS reverse proxy ที่ port 443 และผ่าน Security/Owner sign-off; ดู [Public Deployment Runbook](docs/public-deployment-runbook.md)

โหมด `CHECKLIST_AUTH_MODE=disabled` ใช้เฉพาะ development ที่ไม่เปิด Public; server ปฏิเสธการเริ่มต้นเมื่อ `NODE_ENV=production` หรือ `CHECKLIST_PUBLIC_MODE=true`. ระบบ Public ใช้บัญชีภายในที่เปิด login และ station scope เสมอ

ก่อนส่ง artifact ให้รัน `node tools/run_all_tests.mjs` ซึ่งค้นหาและรัน API, PostgreSQL integration, local-account/OIDC flow, station authorization, Vehicle proxy, PDF และ regression ทั้งหมดแล้ว จากนั้นตั้ง `CHECKLIST_DIST_DIR` ให้ชี้ไปยัง artifact ใหม่ เช่น `./release/public`; ห้ามใช้ `dist` เก่าที่ไม่ทราบ provenance โดย PostgreSQL integration จะ skip หากไม่ได้ตั้ง `CHECKLIST_POSTGRES_TEST_DATABASE_URL`

ระหว่างพัฒนาใช้ `npm.cmd run dev` แล้วเปิด URL ที่ Vite แสดง (โดยปกติ `http://127.0.0.1:5173`) ได้เช่นกัน ระบบจะอ่านค่าเดียวกันจาก `.env`

ถ้าต้องการเปิดแบบเร็ว สามารถเปิด `index.html` โดยตรงได้ แต่การใช้ server จะใกล้เคียงการใช้งานเว็บจริงกว่า

`VITE_VEHICLE_SEARCH_BASE_URL` เป็นเพียงค่าเริ่มต้นของช่อง API ในสถานีใหม่ URL จริงของแต่ละสถานีกรอกและเปลี่ยนจากหน้าเว็บได้เลย โดยระบบจะเรียก API ของสถานีโดยตรงก่อน จึงไม่ต้องเพิ่ม IP ใหม่ใน `.env` หรือรีสตาร์ตเซิร์ฟเวอร์ทุกครั้ง

ช่องนี้รับได้ทั้ง Base URL เช่น `http://สถานี-api:3005` และ Proxy URL เต็ม เช่น `http://proxy:3005/api?target=http://สถานี-api:3005/api/vehicle/search` โดย Proxy ต้องส่งต่อ HTTP method, JSON body และผลลัพธ์ของ `POST` ให้ครบ ระบบจะใช้ origin ของ `target` เป็นปลายทางสำรองสำหรับภาพและ same-origin proxy

ถ้าปลายทางใดไม่เปิด CORS ระบบจะลองใช้ same-origin proxy เป็นทางสำรองใน local mode ซึ่งปลายทางนั้นต้องอยู่ใน `VEHICLE_SEARCH_ALLOWED_ORIGINS` สำหรับ Public ให้เปิด `VITE_VEHICLE_PROXY_ENFORCE_STATION_TARGET=true` และ `VEHICLE_SEARCH_ENFORCE_STATION_TARGET=true` เพื่อบังคับให้ server เลือกปลายทางจาก `VEHICLE_SEARCH_STATION_TARGETS` ตาม Station Profile/identity ไม่รับ target อิสระจาก browser

เมื่อ production ใช้ Proxy URL ที่ browser ต้องเรียกโดยตรง ให้กำหนดเฉพาะ origin ของ proxy ใน `VEHICLE_SEARCH_PROXY_ALLOWED_ORIGINS` เช่น `http://proxy-host:3005`; ค่านี้ใช้สร้าง CSP `connect-src` และแยกจาก `VEHICLE_SEARCH_ALLOWED_ORIGINS` ซึ่งเป็น allowlist สำหรับ server-side proxy

## สิ่งที่มีใน MVP

- ข้อมูลประจำรอบการตรวจและผู้ตรวจสอบ
- รายการหลักฐานกลาง (Evidence Catalog) 13 หมวด / 123 รายการตรวจ / 170 ช่องหลักฐานตามลำดับเอกสาร โดยถอดหัวข้อที่ต้องแนบวิดีโอ 15 ช่องแล้ว
- การตั้งค่ารายการตรวจประจำสถานี 13 หมวด / 44 รายการ สำหรับเลือกใช้กับสถานี
- รอบใหม่ที่ใช้นโยบาย `equipment-cleaning-v1` สร้างรายการทำความสะอาด 1 รายการต่ออุปกรณ์จริงที่ใช้งานอยู่ เฉพาะ Computer, ตู้ควบคุม, LPR, Fixed/PTZ, NVR และ Database Server โดยบังคับภาพ `ก่อนทำความสะอาด` → `ระหว่างทำความสะอาด` → `หลังทำความสะอาด` อย่างละ 1 ภาพ
- ช่องหลักฐานประกอบการตรวจ (Evidence Slot) แยกต่อช่อง พร้อมสถานะ `ยังไม่ได้ระบุ`, `หลักฐานครบถ้วน`, `ไม่มีภาพถ่าย`, `หลักฐานไม่ครบถ้วน`, `ไม่ได้ติดตั้ง`, `จัดเก็บไว้ที่เครื่องแม่ข่ายประจำสถานี` และ `ไม่เกี่ยวข้อง`
- ข้อมูลประจำสถานี (Station Profile) สำหรับระบุอุปกรณ์จริงของแต่ละสถานี พร้อมรหัส ตำแหน่ง และหมายเลขประจำเครื่อง (Serial Number)
- สร้างรายการตรวจแบบ dynamic ตามอุปกรณ์ที่ใช้งานจริง และแยก Snapshot ต่อสถานีเพื่อไม่ให้ประวัติเก่าเปลี่ยน
- ค่าตัวเลข สถานะรายการตรวจ หมายเหตุ และหลักฐานแยกตามรายการ/ช่องหลักฐาน
- แนบภาพถ่าย วิดีโอ PDF หรือข้อความ พร้อม Preview; local mode ใช้ IndexedDB แบบจัดเก็บภายในเครื่อง ส่วน server mode ส่งไฟล์ผ่าน API ไปยัง filesystem หรือ S3-compatible ตามที่ตั้งค่าไว้
- สรุปความคืบหน้าและรายการที่ต้องติดตาม
- บันทึกอัตโนมัติใน browser localStorage เมื่อใช้ local mode หรือผ่าน `/api/v1/state` เมื่อใช้ server mode; server mode มีคิว draft ชั่วคราวใน IndexedDB เมื่อ API ขัดข้อง
- โหลดข้อมูลตัวอย่าง, ล้างข้อมูลของรอบปัจจุบัน และพิมพ์แบบตรวจ
- แยกหน้าตามขั้นตอนด้วย Hash Route: ภาพรวม, สถานีและอุปกรณ์, รอบการตรวจ, Checklist, Vehicle API review และประวัติ/พิมพ์รายงาน
- สร้างรอบการตรวจแบบชัดเจนพร้อมข้อมูล ณ วันที่เริ่มรอบการตรวจ (Snapshot) และปิดรอบเป็นแบบอ่านอย่างเดียว
- แยกชุดข้อความมาตรฐานกลาง พร้อมเก็บข้อความที่ใช้ไว้ในข้อมูลประจำรอบของแต่ละรอบ

โหมด default ของ MVP ยังเป็นข้อมูลเฉพาะ browser เครื่องนั้น โดยใช้ key เดิม `checklist-mvp-v1`; ใช้เฉพาะ local development/staging เท่านั้น ใน server mode ต้องใช้ PostgreSQL/API และ attachment storage พร้อมบัญชีผู้ใช้ที่ server ตรวจสอบ โดยไม่ import browser storage อัตโนมัติ

## ลำดับการใช้งานแบบหลายสถานีและหลายรอบการตรวจ

1. ไปที่ `สถานีและอุปกรณ์` เพื่อเลือกหรือสร้างโปรไฟล์สถานี
2. กรอกรหัส/ชื่อสถานี และเพิ่มอุปกรณ์จริง เช่น `LPR-01`, `Lane 1` หรือ `Sensor #2`
3. ไปที่ `รอบการตรวจ` แล้วกด `สร้างรอบการตรวจใหม่`
4. เลือก Contract, Work Package และสถานีจากบริบทเดียวกัน พร้อมกรอกข้อมูลรอบ; งานเฉพาะกิจที่ไม่ผูกสัญญาใช้ quick inspection mode ที่ `#/inspections/new?mode=quick`
5. ตรวจข้อมูล ณ วันที่เริ่มรอบการตรวจ (Snapshot) แล้วกดยืนยันเพื่อเปิด Checklist
6. กรอกค่าตัวเลข สถานะ และหมายเหตุในหน้า `รายการตรวจและหลักฐาน` ของรอบนั้น; รายการทำความสะอาดต้องแนบภาพถ่ายก่อน/ระหว่าง/หลังให้ครบ
7. เมื่อหลักฐานครบถ้วน กด `ปิดรอบการตรวจ` เพื่อเก็บเป็นประวัติแบบแก้ไขไม่ได้
8. ไปที่ `ประวัติ / พิมพ์รายงาน` เพื่อเปิดดูข้อมูลประจำรอบเดิมและพิมพ์รายงาน

หน้าปก Contract Work Report จัดทำจาก Contract และ Work Package แยกจากรายงานตรวจสถานีที่สร้างจาก Inspection Round และ Snapshot

หน้าการตั้งค่ารายการตรวจประจำสถานีแสดง 13 หมวด / 44 รายการ แยกจากรายการหลักฐานกลางปัจจุบัน 13 หมวด / 123 รายการตรวจ / 170 ช่องหลักฐาน สำหรับข้อมูลประจำรอบที่ใช้นโยบายทำความสะอาด ระบบจะตัดช่องทำความสะอาดแบบรวม/ซ้ำและพื้นที่ที่ไม่ใช่เป้าหมายอุปกรณ์ออก แล้วสร้างรายการต่ออุปกรณ์จริงแทน ระบบจะขอให้ดาวน์โหลด Local Backup ที่รวม JSON และไฟล์ IndexedDB ก่อน migration ลบหัวข้อวิดีโอเดิมจากฉบับร่าง/ประวัติ/ข้อมูลประจำรอบ; หาก Backup ไม่สำเร็จจะไม่ลบข้อมูล ช่องเอกสารที่อาจรับวิดีโอยังใช้งานได้ตามเดิม ส่วนข้อมูลประจำรอบ/ฉบับร่างที่ผ่าน migration จะไม่แสดงหัวข้อวิดีโอเดิมแล้ว ช่องที่ผูกกับอุปกรณ์จริงแล้วไม่พบอุปกรณ์ในข้อมูลประจำรอบจะเป็น `ไม่เกี่ยวข้อง` และไม่รวมในความคืบหน้า รายการที่ยังไม่กรอกจะเป็น `ยังไม่ตรวจ` และหลักฐานที่ยังไม่ระบุจะเป็น `ยังไม่ได้ระบุ`

ช่อง `ผู้จัดทำรายงาน`, `ผู้ตรวจสอบรายงาน`, `ผู้มีอำนาจลงนาม` และ `วันที่ลงนาม` เป็นข้อมูลลงนามรายงานเท่านั้น ไม่ใช่ขั้นตอนการอนุมัติของระบบ

การแก้ Station Profile มีผลกับรอบที่จะสร้างใหม่เท่านั้น รอบเดิมอ่านจาก Snapshot ของตัวเอง อุปกรณ์ที่เคยถูกอ้างอิงใน Snapshot แล้วจะลบไม่ได้ ให้ใช้ `ปิดใช้งาน` แทน

## การแก้ชุดข้อความมาตรฐานกลาง

แก้จากหน้าเว็บได้โดย:

1. เปิดเมนู `สถานีและอุปกรณ์`
2. ไปที่แผง `ชุดข้อความมาตรฐานกลาง`
3. เลือกแท็บ `รายการตรวจและหลักฐาน` หรือ `การตั้งค่ารายการตรวจประจำสถานี`
4. ค้นหาหมวด/รายการ แล้วแก้ `ชื่อหมวด`, `ชื่อรายการ`, `หน่วย` หรือ `คำอธิบาย`
5. ระบบบันทึกอัตโนมัติใน browser เครื่องนี้ ไม่ต้อง build ใหม่

แท็บ `รายการตรวจและหลักฐาน` ควบคุมข้อความของ 13 หมวดและรายการหลักฐานกลางปัจจุบัน 170 รายการที่ผู้ตรวจสอบเห็นจริง ส่วนรายการทำความสะอาดต่ออุปกรณ์จริงและชื่อช่วงก่อน/ระหว่าง/หลังมาจากนโยบายกลางและไม่ถูกเขียนทับด้วยชุดข้อความมาตรฐานกลาง ส่วนแท็บ `การตั้งค่ารายการตรวจประจำสถานี` ควบคุมข้อความของ 13 หมวดและ 44 รายการที่ใช้เปิด/ปิดรายการต่อสถานี ชื่อหมวดของสองแท็บแยกกัน

ข้อความที่แก้มีผลกับรอบการตรวจใหม่เท่านั้น รอบเดิมและฉบับร่างเดิมอ่านจากข้อมูลประจำรอบของตัวเอง หากต้องการกลับไปใช้ค่าเริ่มต้น ให้กด `คืนค่าเริ่มต้น` ในแท็บนั้น

เมื่อใช้ local mode ชุดข้อความจะอยู่ใน `localStorage` ของ browser และไม่แชร์ข้ามเครื่อง ส่วน server mode จะเก็บผ่าน API ตามบัญชี role และ station scope ที่ server ตรวจสอบ; บัญชีภายในใช้ PostgreSQL และ OIDC เป็นทางเลือกขององค์กร

ห้ามเปลี่ยน `id`, รหัสหมวด, ค่า status, `fieldType`, `inputType`, `sourceOrder`, `legacyIds` หรือการผูกอุปกรณ์กับรายการตรวจ (Asset mapping) เพราะเป็นรหัสทางเทคนิค/กติกาข้อมูล ไม่ใช่ข้อความแสดงผล การแก้ `sourceLabel` ของ PDF ต้องทำเป็นการเปลี่ยนแม่แบบแยกต่างหาก
